## Tier 2 — No new data needed, but needs new aggregation logic
- [ ] Frequency (days active/month) — derive from player_activity_master.csv. The rolling window (84 days, weekly_player_kpis.py line 35) comfortably covers the current + prior ~2 complete months, so this is safe if computed right after each month-end. It is NOT safe for historical/YoY frequency — the YoY slice is only 7 days wide and the file is pruned every run, so past months roll off permanently. Fix: compute Frequency as soon as a month completes and persist just the aggregated monthly result to a small new permanent CSV, decoupled from the prune cycle — don't try to keep raw daily rows around longer just for this.
- [ ] Stickiness (daily avg actives/actives) — same source and same constraint as Frequency above (needs daily grain within a period); same fix — compute at month-close and persist the aggregate separately. Note this is NOT the same as the existing p12_actives_avg metric, don't reuse that logic.
- [ ] Widen player_activity_master.csv's rolling window from 84 → 98 days (14 weeks) in weekly_player_kpis.py (line 35). Cheap, one-line change (~2 extra weeks of rows). Needed to fix Reactivated_players_90 below — do this regardless of whether Frequency/Stickiness end up needing it.
